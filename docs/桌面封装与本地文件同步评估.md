# NoteFlow 桌面封装与本地文件同步评估

评估日期：2026-07-15

## 结论

当前阶段继续采用 **Web + PWA 优先**，不立即引入 Electron/Tauri，也不默认开启本地 Markdown 文件夹双向同步。

原因是 NoteFlow 的核心数据不仅包含 Markdown，还包含版本、索引、草稿、修改预览、长期记忆、附件和 Agent Checkpoint。直接把 Markdown 文件夹作为主数据库，会造成元数据丢失、跨设备冲突和索引状态不一致。现有 PWA 已覆盖安装入口、离线壳、移动快速记录和断网编辑队列，桌面封装目前带来的收益不足以抵消发布、签名、自动更新和文件权限维护成本。

## 推荐演进路线

1. 保留 Markdown/ZIP/JSON 导入导出，作为透明、可迁移的数据出口。
2. 若用户需要 Obsidian/Logseq 互操作，先增加“导出到 Markdown 文件夹”和“从文件夹单向导入”，不做静默双向覆盖。
3. 双向同步必须先具备文件哈希、服务端版本号、删除墓碑、冲突副本、附件 sidecar 和人工合并界面。
4. 只有出现系统托盘、全局快捷键、原生分享菜单、本地全文索引或受控文件夹监听等明确需求时，再采用 Tauri 2 封装现有前端；不另写一套桌面 UI。
5. Electron 仅在必须使用成熟 Node 原生生态且 Tauri 插件无法满足时考虑。

## 本地文件映射建议

- 正文：`notes/<slug>.md`
- 稳定标识与版本：Markdown frontmatter 中保存 `note_id`、`version`、`updated_at`
- 附件：`assets/<note_id>/...`
- 删除：`.noteflow/tombstones.json`
- 同步状态：`.noteflow/index.json`，记录内容哈希和最近同步版本
- 冲突：生成 `<slug>.conflict-<device>-<timestamp>.md`，绝不静默覆盖

## 启动下一阶段的门槛

满足以下任意两项后再安排桌面封装：

- 超过 30% 活跃用户持续使用 PWA 安装模式；
- 全局快捷键/系统托盘成为高频诉求；
- 本地 Markdown 文件夹互操作成为明确付费或留存需求；
- 浏览器文件权限限制实际阻塞核心工作流；
- 已建立桌面签名、自动更新和崩溃收集发布能力。

本次评估任务至此完成；桌面封装和双向文件同步属于后续独立里程碑，不是当前版本的未完成缺陷。
