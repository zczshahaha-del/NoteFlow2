# NoteFlow 全栈安全审查（2026-10-05）

审查基线：`7a3a155`，范围为当前仓库前端、后端路由 / 服务 / Repository、鉴权、附件、AI / RAG / 记忆、依赖和部署模板。本轮仅审查与记录，没有修改业务代码、升级依赖或部署。

## 1. 结论与边界

存在应在开放公网 / 多用户使用前修复的问题。优先级最高的是未验证账号合并、前端 HTML 清理绕过和运行时编辑器依赖告警。其次是旧凭证撤销缺口、费用 / 资源滥用、附件和运维边界。

这是源码审查、离线合成验证和依赖公告匹配，不是完整渗透测试、合规认证或“系统没有其他漏洞”的保证。没有操作真实账号、笔记、邮件、模型接口或数据库；没有访问正式浏览器会话或扫描公网主机。风险等级为本项目处理优先级，不是独立计算的 CVSS。

所有问题当前均未修复。依赖“版本命中”不等于本项目已出现实际利用，公告数量也不等于独立漏洞数量。

## 2. 已确认问题与处理建议

### AUTH-02 / AUTH-04：未验证邮箱合并存在账号预劫持风险（高）

- 现象：旧 `/api/auth/register` 仍允许不验证邮箱就设置密码并获得会话。邮箱所有者随后通过验证码首次登录，会认领同一个用户，但旧密码、旧会话仍保留。
- 根因：`server/app/routers/auth.py:310` 的注册不要求邮箱所有权；`:404`～`:419` 的验证码登录只设置 `email_verified_at`，没有重置不可信凭证、撤销会话。密码登录也没有要求已验证邮箱。
- 影响 / 条件：攻击者在真实所有者首次验证之前用其邮箱注册；所有者验证后开始存笔记，攻击者仍可能凭原密码 / 会话访问。不是“知道邮箱即可立即登录已有验证账号”。
- 验证：直接调用实际确认函数，数据库与邮件校验用合成对象 / mock；首次验证后原密码哈希不变，只执行用户查找，没有查询撤销旧会话。密码登录保留该哈希的分支经源码核对。
- 建议：注册先验证邮箱再激活；首次认领未验证旧账号必须消除旧密码和旧会话，保留原用户 ID / 笔记但不能无条件继承身份信任。既有账号迁移应先备份、明确可信认领规则，不能简单删除历史账号。
- 状态：未解决，重开原 AUTH-02 / AUTH-04，不重复创建同义 SEC 条目。原功能 / 迁移可用证据保留，不再等同安全闭环。

### SEC-01：AI / 草稿 / 修改预览 HTML 清理可以绕过（高）

- 现象：恶意 HTML 链接经过 `renderChatMarkdown()` 后仍能保留可执行 URL；用户点击后可能在应用页面权限下执行脚本。
- 根因：`src/utils/chatMarkdown.ts:130` 采用手写黑名单，URL 检查只做 `trim().toLowerCase().startsWith(...)`，未处理浏览器 URL 解析时忽略的控制字符。输出用于 AIPanel、AIDraftWorkspace、EditPreviewWorkspace 的 `dangerouslySetInnerHTML`。
- 验证：实际源码在独立 JSDOM 的 `https://audit.invalid/` 页面执行，合成链接经过清理后协议仍为脚本协议；点击只设置一个内存标记，确认标记被执行。无网络、无用户数据、无真实凭证。
- 影响 / 条件：需要不可信内容进入 AI 回复 / 预览并被用户点击。HttpOnly Cookie 能防止直接读取 Cookie，但不能阻止同源脚本代用户请求笔记或执行操作。
- 建议：使用维护中的 HTML sanitizer 与允许列表，集中管控链接 / 图片协议、SVG / MathML、表单等；新增绕过与正常 Markdown 回归。前端 HTML 响应增加兼容现有应用的 CSP，作为额外防线。
- 状态：未解决。后端 API 的 CSP 不覆盖 Nginx 返回的前端 HTML，不能作为此问题已被防御的依据。[OWASP HTML 清理建议](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)。

### SEC-02：无 sid 的旧 JWT 不受服务端会话撤销控制（中高，条件性）

- 现象：退出、改密码和设备撤销主要撤销 UserSession；无 `sid` 的仍有效旧 JWT 能继续访问普通业务接口，也能重新迁移出新会话。
- 根因：`server/app/deps.py:52` 仅在 `sid` 存在时查会话；`auth.py` 的旧令牌迁移接受无 sid 的有效 token。`src/services/api.ts` 迁移失败还会退回 Bearer 使用。
- 验证：使用专门的合成签名密钥创建 token；无 sid 时通过且数据库查询次数为 0；带不存在 / 已撤销 sid 的对照返回 401。未使用真实密钥。
- 条件 / 限制：需要已有仍未过期的合法旧 JWT，不能无密钥凭空伪造。普通新 sid 会话的撤销校验仍有效；真实历史 token 的存量和最长有效期未统计。
- 建议：普通业务接口必须要求有效 sid；迁移设明确截止期 / 一次性标记，密码重置等事件增加用户凭证版本或吊销时间校验。上线迁移要先评估兼容影响，不直接轮换密钥导致全部用户无提示退出。
- 状态：未解决；AUTH-07 / AUTH-11 的“全部旧凭证失效”结论需收紧。

### SEC-03：附件 MIME 校验可绕过（中，已有 CSP 缓解）

- 现象：大小写变体的 HTML MIME 和 XHTML MIME 可上传，并以客户端给定的 MIME、`inline` 返回。
- 根因：`server/app/routers/attachments.py:70` 信任 X-Content-Type，并用区分大小写的两个前缀黑名单，未验证真实文件内容或建立允许列表。
- 验证：mock 存储、实际路由 / 中间件的独立 ASGI 测试确认普通小写 HTML 返回 415，而变体返回 200；下载保持 inline / HTML MIME。
- 缓解 / 边界：`services/observability.py:170` 会给 API 响应添加 `default-src 'none'` CSP，完整链路已核对其存在。因此本轮只确认类型校验缺陷，不声称已证实附件脚本在正式应用执行。未进行真实浏览器附件执行测试。
- 建议：MIME 规范化 + 内容检测 + 允许列表；仅确认为安全图片等的类型 inline，其余强制下载，必要时使用不带应用 Cookie 的独立附件域名；保留 CSP / nosniff。
- 状态：未解决。[OWASP 上传安全](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) 明确不应信任上传者声明的 Content-Type。

### SEC-04：私有附件链接没有有效期 / 独立撤销机制（中）

- 现象：取得完整签名 URL 的人不需要登录即可读取附件；退出、改密码、撤销会话不使链接失效。
- 根因：`attachments.py:44` 的签名只绑定附件 ID，用 JWT_SECRET 生成固定 HMAC，未包含过期时间或权限版本；`/content` 路由只校验签名。
- 验证：源码及独立 ASGI 的无认证 signed-content 路径确认。未尝试猜测签名或读取真实附件。
- 条件 / 限制：必须已经得到有效完整链接；不是公开附件 ID 就能读取。删除附件或改变签名密钥会改变结果。图片持久链接若是产品有意能力，必须明确其 bearer-link 保密语义。
- 建议：短时授权 URL、独立签名密钥和附件权限版本；笔记存附件 ID 而非长期授权链接，由加载接口刷新。设置明确的撤销与缓存策略，避免靠轮换登录密钥管理附件。
- 状态：未解决 / 待确认产品授权语义。

### SEC-05：AI、邮件与存储资源限制不一致（中高，公网多人场景优先）

- 现象：聊天 / 一键笔记有请求限流，但直接创建 / 修订 AI 修改预览没有同等限制；RAG 搜索 / 批量评估 / 重建、草稿排队和改绑邮件亦不统一。大量不同请求可消耗模型费用、数据库连接、队列与磁盘。
- 根因：限流主要挂在少量路由，不是所有昂贵服务的共享预算。`routers/edits.py:589` 仅鉴权，随后调用模型；`auth/email-change/request` 的冷却按目标邮箱，不限制同一账号给不同邮箱发信。附件只有单文件上限，没有用户总容量 / 文件数配额。
- 验证：真实路由依赖树确认修改预览、RAG eval、改绑发信只有 get_current_user；调用链核对到模型 / 检索 / 邮件。没有压测、发送邮件或调用模型。
- 现有防线：聊天每分钟限流、模型输出上限、草稿 worker 单任务串行和同文件上传限制存在；不是“全部无限并发”。但不能阻止多账号 / 多请求排队、总费用与容量滥用。
- 另一个边界：附件以 `Body(bytes)` 先完整读入再检查长度；外层 HTTPS Nginx 有 12m 上限，但内层 Nginx 未统一声明该值、默认 body 上限可能更小，直连后端没有流式总量防护。大文本字段也缺少统一长度预算。
- 建议：服务级按用户 / IP / 全局预算及并发限制，日 token / 费用上限、存储配额、队列公平调度与积压上限；统一网关 body 上限并在流读取阶段拒绝超限。避免依赖前端禁用按钮防滥用。
- 状态：未解决，容量 / 费用影响尚未通过负载测试量化。[OWASP 资源耗尽防护](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html)。

### SEC-06：匿名不同 404 路径造成无界指标内存增长（中）

- 现象：每个不存在的不同 URL 都成为独立指标标签和 deque，随请求持续增长，没有全局键数量上限。
- 根因：`services/observability.py:157` 在未匹配路由时以原始 path 为键；request counts、duration totals、samples 的字典无淘汰。单 deque 的 2000 条限制不限制键数量。
- 验证：独立空 FastAPI + 实际中间件，发送 32 个合成不同路径，得到 32 个 404，同时新增 32 个指标键。未请求运行中的系统或执行高负载攻击。
- 建议：未匹配路由统一归 `unmatched`，限制标签基数 / 总键数量；在网关增加匿名请求频率保护。监控本身不能成为资源耗尽入口。
- 状态：未解决；没有测量导致实际 OOM 所需请求量。

### SEC-07：详细诊断匿名公开，业务监控未做管理权限分层（低中）

- 现象：`/api/diagnostics` 和 health checks 返回内部数据库 / Redis 地址、配置与模型信息；diagnostics 每次还探测数据库 / Redis。`/metrics` 虽然需登录，但普通账号可看全局汇总。
- 根因：`routers/health.py:28` 无鉴权；`services/diagnostics.py` 的 public_config_snapshot 直接返回运维信息。当前没有 admin / 运维角色隔离。
- 验证：mock 诊断配置、实际独立路由匿名返回 200；metrics 匿名对照返回 401。没有输出真实内部地址、密钥或诊断快照。
- 影响：辅助侦察 / 全局运营信息暴露 / 反复探测资源，不等于 API Key 或笔记直接泄漏。
- 建议：公共 health 仅返回最小 liveness / readiness，详细诊断和全局指标仅内网 / 管理员；诊断结果短时缓存。区分普通用户自己的用量与全局运维。
- 状态：未解决。

### SEC-09：ZIP 导入只信任声明大小，解压上限可绕过（中，需用户导入）

- 现象：声明极小尺寸的 ZIP 条目实际解压超过 8 MB 后仍被接受；总解压大小也没有限制。
- 根因：`src/utils/importKnowledge.ts:24` 的 inflateRaw 使用 arrayBuffer 一次性收集完整解压流；parseZipMarkdown 只检查中央目录声明的 uncompressedSize，解压后没有实际计数 / 总预算 / 一致性校验。
- 验证：离线内存合成 ZIP，压缩包 8272 bytes，声明条目 1 byte，实际解析并接受 8,388,609 bytes（超过 8 MiB）。未创建、导入或上传真实文件，没有进行大规模炸弹测试。
- 影响 / 条件：用户主动导入不可信备份，可导致浏览器卡顿或内存耗尽；不是服务器任意文件写入，也不是无需交互的远程执行。
- 建议：边解压边计数并可取消，设实际单项 / 总量 / 压缩比预算；校验结构、内容长度和条目数量，在 worker 中解析，JSON 树也限制深度和总条目数。
- 状态：未解决。

## 3. 既有部署风险与其他优化

1. **OPS-03 未闭环**：生产覆盖文件确实移除数据库 / Redis / 后端映射，但基础 Compose 仍绑定所有网卡、Redis 无密码且默认 development；backend 自身也监听 0.0.0.0。误用基础文件对外部署会暴露危险开发默认值，包括已知 JWT 默认密钥与邮件失败时返回 developmentCode。生产正确设置有启动校验，不能据此断言当前服务器正在泄漏。建议开发端口仅绑定回环、生产入口 fail-closed，并验证服务器实际有效 Compose / 防火墙 / 环境模式。沿用 OPS-03、AUTH-05，不重复新增同义项。
2. **CSRF / Host 防御**：有 SameSite=Lax、CORS 和 API 安全响应头；未发现独立 Origin / CSRF token / TrustedHost 校验。建议对状态写入与高风险账号操作增加显式防护及重新认证。未做浏览器跨站验证，不标为已证实 CSRF。
3. **代理限流身份**：需要实测两层 Nginx 到 Uvicorn 的可信代理链，避免所有用户共享代理 IP 限额或信任伪造 X-Forwarded-For；当前只确认会话 IP 直接取 XFF，未验证生产实际链，不能断言限流已被绕过。
4. **浏览器防线**：Nginx 的前端 HTML 缺少 CSP / frame-ancestors；API 已有 CSP、nosniff、DENY，不能说全系统都没有安全头。HTTPS HSTS 要在 TLS / 续期验收后启用，CSP 要兼容编辑器、样式、图片和连接，避免直接套 API 的 default-src none 把应用禁用。
5. **隐私和隔离**：AI cache 按完整请求 body hash，没有显式用户 namespace；本轮没有证明跨用户泄露。建议用户分区、清理留存策略、AI 对外发送内容明确说明与敏感信息确认。检查过的笔记 / 草稿 / 修改 / 会话 / memory Repository 和 RAG SQL 均有 user_id 过滤；SQL 使用绑定参数。建议补真实双账号负面集成测试及 PostgreSQL RLS 纵深隔离。
6. **最小权限 / 运维**：容器未声明非 root USER、镜像 tag 非 digest、完整 Python lock / CI 缺失。建议非 root、最小数据库权限、read-only 根文件系统（保留必要可写卷）、镜像扫描 / SBOM / 自动告警。它们是纵深防御，不是已经证明容器逃逸。
7. **恢复与审计**：GIT-05 / OPS-11 的真实备份恢复、生产验收仍未闭环。增安全事件日志 / 异常登录告警 / 密钥轮换流程 / 加密离机备份；日志默认不记录完整提示词、笔记或授权内容。本轮检查当前 tracked 文件未发现 .env / 私钥 / 本地数据库文件，不等于 Git 全历史已通过 secret scan。
