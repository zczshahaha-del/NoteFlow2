# 记忆与上下文架构审查 · 2026-10-15

状态：审查与建议，未实施。用户要求分析架构，不能将本文当作改造已获批准或问题已修复。关联 AI-10 / AI-11；未改用户记忆、模型、接口、存储结构或运行服务。

## 结论

现有 PostgreSQL 记忆真相、账号归属、状态与审计、Outbox 索引同步，以及 LangGraph 任务运行结构可以保留。主要缺口在读取职责：聊天主链路把“本次需要参考什么用户背景”过度交给主意图规划决定，没有独立的基础上下文契约；语义检索还受到提前截断的关系库候选集合约束。

不建议靠“遇到你好就取姓名”的关键词补丁，也不建议每轮注入整份个人资料。应建立统一、可追踪、受策略约束的上下文组装过程，同时保留唯一语义 TurnPlan，不增加第二轮模型规划。

## 当前链路与已核实证据

```text
当前消息 / 最近历史 / 页面状态
  → langgraph_turn：模型规划 → 强类型校验 → TurnPlan
  → 路由普通聊天 / 笔记问答 / 创建 / 修改 / 记忆管理
  → 只读图：仅在计划包含 user_memory 时召回记忆
  → 模型回答 → MemoryWriter → agent_done

记忆读：关系库候选排序 / 截断 → 合格状态筛选 → Mem0 排序
        → 仅接受原候选 ID → 格式化成 memory_context
记忆写：提取候选 → 策略 / 去重 / 规范键 → PostgreSQL + Outbox → Mem0
```

1. AI-10 的真实问候快照已证明：记忆开启，基础称呼在设置中有效，但本轮 context_sources=[]、memory_context 为空。没有读到与读到后模型忽略是不同问题，本次属于前者。
2. `turn_planner.validate_turn_plan` 只对显式记忆意图补齐来源；`langgraph_readonly.memory_recall` 将 user_memory 来源作为前置门槛。普通聊天允许模型选择记忆，但没有基础称呼可靠性保证。
3. `memory.domain.find_memories` 查询未删除记录，包括 pending / archived 等，排序后先截断。`runtime.resolve_memory_read` 后续才按 active / 未过期 / 内容策略过滤。合成正式函数诊断：8 条较高优先候选均 pending、后面有 1 条 active，limit=8 时最终有效记忆为 0。
4. 同一诊断中，9 条有效记录的第 9 条与查询语义相关，但关系库先取前 8 条；Mem0 替身返回第 9 条 ID，最终仍被 allowed_ids 舍弃。该边界证明语义召回无法救回预候选之外的有效记录，不代表用户姓名问题由它导致。
5. 普通聊天、生成笔记和编辑预览分别消费 `query_memories_for_agent`、`MemoryContextService.context`、`build_memory_context`。它们的门槛、候选上限、格式与是否经过 Mem0 不一致，应汇入同一策略服务，而不是各自叠加修补。
6. 只读图的 MemoryWriter 发生在回答之后，但仍被 await，且位于 finalize / agent_done 之前。已有 Outbox 只说明索引同步异步，不代表记忆提取已移出交互关键路径。此处是源码层面的尾部延迟风险，未测真实模型耗时，不宣称已经解释全部聊天等待。

## 目标：区分三种用途

| 用途 | 决策与读取 | 边界 |
| --- | --- | --- |
| 基础用户上下文 | 后端固定策略选择少量已确认字段，按规范键确定读取 | 记忆关闭时不读；称呼、语言、表达偏好分开；不默认加载年龄、学历、健康等全部画像 |
| 当前任务相关记忆 | 唯一 TurnPlan 提供检索意图、范围 / 键，检索服务返回相关候选 | 始终做账号、状态、作用域、时效与可信度校验；受文本预算约束 |
| 显式记忆管理 | 明确读 / 列出 / 更新 / 删除 / 关闭，由业务服务执行 | 写操作有独立确认、审计与幂等语义，不能因一次检索或失败重试重复执行 |

这是后端职责划分，不要求给用户增加三种聊天模式。

基础字段的策略可以是固定规则，字段值必须来自当前账号有效记录。称呼偏好与法定姓名应能区分，用户本轮临时称呼只影响本轮；记住了姓名不意味着每次回复都强行叫名字。

## 统一 ContextAssembler

建议先作为现有 Memory 包和 AI 编排服务中的明确接口建立，不新建微服务，也不更换 Mem0 / LangGraph。

```text
请求权限、记忆开关、账号 / 会话身份
  ├─ 基础字段策略 → 确定性读取
  └─ TurnPlan → 当前任务相关检索
最近会话 / 页面 / 业务任务状态
  → ContextAssembler：去重、冲突、用途、来源、预算
  → 回答 / 草稿 / 修改模型
```

组装结果应包含结构化条目、来源和读取状态，最后才转成模型消息；不只在多处拼一个字符串。

- 明确区分 disabled、not_requested、found、empty、error 等读取结果。服务异常不能等同“没记住”，未查询也不能解释为“从未告诉过我”。
- 规则优先级：系统与业务边界 > 本轮明确要求 > 已确认记忆 > 推断候选。记忆是背景数据，不升级为能覆盖业务规则的指令。
- 基础字段保留独立小预算；相关经历 / 项目按相关性分配预算。历史消息、笔记证据、用户偏好分别标识，避免互相冒充来源。
- 用户可见模式维持现状。全库问答继续只把笔记作为事实证据；允许的语言 / 排版偏好可另行约定，不把个人记忆混进笔记事实或引用。
- 生成 / 编辑优先消费写作偏好、约束和任务背景；未经本轮要求，不把个人姓名等信息写入正文。
- 可并行读取基础字段和执行规划；相关检索按计划执行。无需为“是否知道称呼”再调用一次模型。

## 调整候选顺序

基础规范键：关系库按账号 / 键 / 有效状态精确读取，做冲突处理，不依赖向量相似度寻找名字。

相关记忆：Mem0 在当前用户与作用域内产生较宽候选，随后回关系库重新核验归属、active、删除、过期、版本 / 规范键和内容资格，再排序截断。索引只是候选来源；关系库仍是最终真相。不能仅因为命中记录不在预取前 8 条就认定不可用，也不能信任索引里残留的已删除记录。

关系库检索回退也必须先排除不合格记录再占最终预算。Mem0 不可用时返回明确 degraded 状态并使用受限的安全回退，而不是无差别塞入高重要度画像。

## 写入和一致性

保留当前只从用户原话提取、pending 不生效、规范键与审计机制。单值覆盖还应区分名字与偏好称呼；阶段状态、年龄等需要有效时间 / 观测时间约定，不把所有值视为永久事实。

显式“记住 / 改称呼 / 忘记”在主库提交后再确认，下一轮应立即可见。普通聊天的隐式提取可移到持久队列；不能用易丢失的进程内 fire-and-forget 替代。需要源消息 ID 幂等、失败重试、去重、关闭 / 删除后的版本屏障，防止旧队列重新写回已经遗忘的信息。Mem0 同步可沿用已有 Outbox。

异步提取的最终一致性不能破坏会话中的新信息：本轮明确要求和近期会话状态先参与当前回答，但这不等于读取时回填历史姓名、暗中迁移旧数据或直接写长期记忆。

如引入基础字段缓存，键应包含账号与记忆版本；更名、停用、删除、关闭记忆及时失效。缓存不是本轮前置需求，先确定一致性契约。

## 观测与验收

每个 run 记录来源选择、基础 / 相关记忆条数、读取状态、过滤原因类别、耗时与版本；不记录明文个人资料到普通日志。读取失败率、基础字段覆盖、语义命中和回答是否矛盾需分开检查，不能只看模型有没有输出或数据库里有没有记录。

验收至少覆盖：

- 新对话问候能使用已有称呼；没有称呼时不编造；关闭 / 停用 / 删除后不使用。
- 显式更名立即可见，本轮临时称呼不覆盖永久值；账号切换不串记忆。
- pending / 过期项不会挤占 active；语义相关项不被预截断丢弃；索引残留已删除项不能复活。
- 普通聊天不自动转全库搜索；全库事实仍来自笔记；表达偏好不改变事实答案。
- 显式记忆失败说明实际状态，普通回复可按用途降级；后台提取不阻塞回答结束。
- 重试不重复记忆写入 / 任务副作用，迟到写入不会越过删除或关闭屏障。

建议实施顺序：先统一读取策略与结果状态、修基础上下文和候选顺序，再迁移生成 / 编辑入口，最后把隐式提取移出关键路径并完善观测。每步独立验证与提交，不一次性重写存储或批量清理历史记忆。
