# 聊天流式体验排查

日期：2026-10-09。用户反馈聊天 SSE 输出很卡、不像连续输出。前半部分保留首轮只读诊断证据；用户明确是“停一下再整段跳出来”后，同日实施前端显示修复，见末节。两轮均未重新发送真实模型请求，未修改模型参数、会话或笔记数据。

## 已确认的事实

1. SSE 已实际接入。`src/services/aiStream.ts` 每次 `reader.read()` 后按行解析，遇到正文 delta 立即回调，没有“攒完整答案才显示”的客户端门槛。后端普通回答通过 `langgraph_readonly.py` 的队列转发提供商片段，不是先 `join` 完整正文再统一发送。
2. `src/store/index.tsx` 的普通 `sendMessage.onDelta` 每个片段都创建新的消息数组。`AIPanel.tsx` 在整个数组上逐条调用 `renderChatMarkdown`；没有给不变的历史正文保留解析结果。解析包含 Markdown、临时 DOM 清理、代码高亮 / 工具栏和引用遍历，不只是字符串拼接。
3. 聊天滚动 effect 依赖整个消息数组。吸底状态下每次更新都读取 `scrollHeight` 并调用 `scrollTo`，与新正文布局同时发生；这是可优化的频率，不等于已证明滚动是本次严重卡顿的根因。
4. 显示层直接展示收到的片段，没有独立的呈现队列。因此较大的提供商片段会整体出现。`stream_chat` 命中应用答案缓存时，`cached_delta` 甚至一次返回全部缓存正文；这是缓存路径的确定行为，但本轮未确认用户这次是否命中缓存。
5. 开始回答前，普通 `chat` 会等待 `invoke_turn_graph` 完成意图规划。`turn_planner.py` 通过非流式 `complete_chat` 得到规划 JSON，之后才返回回答流。规划和普通回答未显式覆盖 thinking；[DeepSeek 官方说明](https://api-docs.deepseek.com/guides/thinking_mode/)说明默认思考开启、默认强度 high。源码说明存在先规划及默认思考的等待环节，不能据此断言这次实际等待了多少秒。

## 隔离浏览器对照

脚本：[scripts/chat-stream-audit.mjs](../scripts/chat-stream-audit.mjs)。使用正式 AIPanel、正式 Markdown renderer、正式 askAIStream / apiFetch，生产构建 CSS；selector 快照和 fetch 是合成替身。全新浏览器上下文、所有实际网络阻断，不打开 localhost 或用户浏览器，不读取真实消息。

合成流每约 25ms 投递一段，共 30 段；历史回答含段落、表格、代码与高亮。最终一次本机检查记录如下，数值只代表该夹具及本机，重跑时计数和耗时可能受调度影响：

| 历史回答数 | 收到 / 回调片段 | Markdown 调用 | 其中不变历史调用 | 总解析耗时 | 吸底滚动调用 |
| --- | --- | ---: | ---: | ---: | ---: |
| 0 | 30 / 30 | 31 | 0 | 10ms | 30 |
| 10 | 30 / 30 | 407 | 370 | 95ms | 30 |
| 30 | 30 / 30 | 1147 | 1110 | 224ms | 30 |

三组均无 pageerror、无外部请求、无超过 50ms 的帧间隔或 longtask；最大帧间隔约 17ms。合成 enqueue 到解析回调的最大延迟分别为 2 / 0 / 0ms，**不包含真实网络或模型延迟**。较长历史时回调间隔最大约 40ms，但本检查没有复现用户所述严重卡顿。确认的是不随历史增长而必要的重复工作，不能把它当作用户本次端到端根因已唯一确定。

初版滚动探针累加到复制前的对象，报告错误地显示 0；修正探针引用后重新运行，正式吸底路径均为 30 次。产品没有为探针改动，原错误数值不作为验证证据。

复跑前先 `npm run build`，随后执行 `node scripts/chat-stream-audit.mjs`。没有安装 Playwright 时，可用环境变量 `NOTEFLOW_PLAYWRIGHT_MODULE` 指定已有运行库，`NOTEFLOW_BROWSER_EXECUTABLE` 指定已安装浏览器；不要为此读取现有浏览器 profile。脚本本身没有真实服务或模型验收能力。

## 建议的独立修复范围

第一步先优化显示层：不变的历史正文按消息隔离复用，当前输出合并同一帧内的更新，吸底滚动跟随实际呈现帧；核对停止、失败、会话切换、完整最终文本、引用和代码动作不受影响。

若反馈主要是整段跳出，再评审自适应呈现：收到的真实内容与可见内容分开，允许短时平滑大块输出但限制积压；后台 / 减少动效 / 完成 / 停止必须有明确收束策略，不为表现持续生成而故意拖长等待。

若主要是首字慢，需要单独实测规划 / 模型的时序，再讨论规划是否使用非思考或较低强度。不能擅自跳过意图识别，不能将关闭思考当作纯 UI 改动。

## 同日实施：自适应打字机显示

范围：只处理普通聊天收到正文后的呈现与历史复用；不改模型、thinking、意图规划、SSE 协议、后端或其他工作区。用户当前反馈是大块文字跳出，不是要求在未收到正文时伪造文字。

- [ChatTextPresentation](../src/utils/chatTextPresentation.ts) 保留完整目标文字，以完整字素为单位推进可见部分，避免截开 Emoji、组合字符；正常小片段及时跟上，突发大块自适应加速，完成时设置 900ms 收束期限，不制造长时间积压。
- [useChatPresentation](../src/hooks/useChatPresentation.ts) 将本地可见正文与 [store](../src/store/index.tsx) 中的完整正文分开；不截断保存或下一轮上下文。动画只用于新回答，既有历史立即显示；首个真实字素立即隐藏思考提示。
- 正常完成的显示尾部仍保留停止入口；点击立即展示已收到全文，后端已结束时不再次发取消。主动停止、失败、校验后替换正文、切换会话和清空都有明确收束；后台 / 减少动态效果直接展现收到的内容，卸载清理动画与监听。
- [AIPanel](../src/components/AIPanel.tsx) 按消息缓存 Markdown，滚动依赖可见正文而不是整个原始数组；正在阅读历史时不强制吸底，输入焦点与草稿不因显示更新丢失。[请求历史](../src/services/aiStream.ts) 明确只发送 role / text，客户端生命周期不进入后端契约。
