## 2. 总体结论

整个开发阶段的问题并不是单一的“页面不好看”，而是五条线同时暴露：

1. 认证最初只有基础邮箱密码表单，验证、找回、迁移和真实邮件链路不完整。
2. 账号、设置、邮箱、设备、数据管理曾堆在同一个小菜单里，信息架构反复调整。
3. 主工作台功能完整，但缺少统一设计系统，正文、AI 面板、草稿和修改预览像不同产品。
4. 本地依赖、预览进程、Docker 镜像网络和低配服务器使“代码完成”多次不等于“环境可用”。
5. 设计探索一度追求新颖而偏离真实产品；后续才恢复“先映射现有功能，再设计视觉语言”的方法。

当前最大的未闭环项有三个：**新版工作台仍停留在设计稿、阿里云生产部署未完成最终运行验收、现有数据尚未形成跨机器迁移包**。

### AI-08：首次大纲请求被 StrictMode 清理后卡在生成提示（部分解决）

现象：2026-10-03 用户报告 MCP 笔记大纲一直卡住。只读检查确认 5173 / 8081 均监听，数据库中对应创建入口任务已 completed、耗时约 2.5 秒；检查点为 waiting_user_confirm、没有 draftId，未查询到 MCP 草稿。入口任务完成仅表示已交接前端，不表示大纲或正文生成完成。用户随后明确要求继续处理未生成的 MCP 笔记，并非确认已恢复；再次只读查询仍无 MCP 草稿和检查点 draftId。未读取用户浏览器内部状态，不能将本次所有运行细节都视为直接复现。

根因：正式 main.tsx 使用 React.StrictMode；AIDraftWorkspace 的首次自动生成先设置 autoOutlineStartedRef=true，而卸载清理立即 abort 当前请求。开发模式的 effect 清理 / 重执行保留该 ref，后续自动生成被标记挡住；AbortError 又不写 errorText。AIPanel 按 configuring 显示“生成中”并禁用打开，而不检查 busy=false，因此出现没有活动请求却一直等待的状态。源码对照确认这段生命周期逻辑在本轮草稿视觉改造前的 83c0021 已存在；不据此排除真实模型链路的其他潜在问题。

验证证据：正式组件经 Vite SSR 装载到新 JSDOM，使用合成 seed / checkpoint 和流式请求替身，所有 fetch 禁止联网、不访问原应用 / 用户会话、不调用模型或写笔记。StrictMode 对照断言：请求一次且被 abort，stage=configuring、busy=false、errorText 空；非 StrictMode 同样请求一次但未被 abort、busy=true。真实数据库仅用 READ ONLY 查询状态及长度，无更新。该证据验证前端可复现根因并与用户现象吻合，不代替用户浏览器端到端验收。

处理：用户要求继续处理后，仅修复 AIDraftWorkspace 的首次自动生成与大纲命令生命周期。启动延迟到可取消的 microtask，StrictMode 第一轮清理不再发请求或设置启动标记；已有生成命令优先，避免自动启动竞争。流式 delta / 请求结束 / 草稿创建返回 / catch / finally 均核对请求归属，取消或切换主题后的旧结果不覆盖新任务。停止当前大纲立即释放忙碌并通过已有失败卡提供重试；未主动取消的 AbortError 按失败反馈，不再无声等待。保留 StrictMode、模型参数、后台生成、正文内容和本轮视觉设计，没有读取或更换密钥、发起真实模型生成、修改数据库或重启服务。

修复验证：新增 npm run test:draft-lifecycle，使用正式组件、开发 React.StrictMode、新 JSDOM 和合成服务；旧代码先在“请求不得被 StrictMode 取消”断言失败，修复后首次 / 非严格挂载、大纲成功创建两章、初始重试命令只发一次、停止后可重试、服务失败 / 空大纲 / 非主动 AbortError、主题切换、旧 delta / finally 不干扰新任务及卸载断言均通过。test:frontend（42 组 / 10 项）、test:editor-ui、build、check:dev-ports 和正式组件离线 test:draft-ui 通过；后者仅证明既有样式与恢复流程，不能代替新增首次生成回归。Node DEP0205 警告沿用 DEV-11。

状态：🟡 部分解决。可复现前端生命周期问题已修复并验证；真实 MCP 大纲生成 / 检查点绑定 / 页面恢复 / 章节正文 / 保存端到端尚未验收，不声称笔记已经生成。此次不绕过既有应用访问限制、不自动重发付费请求；用户需在本地刷新后验收原 MCP 会话。随 fix: 修复首次大纲生成的严格模式生命周期；相关文件 src/components/AIDraftWorkspace.tsx、scripts/draft-lifecycle-test.mjs、package.json。问题与修复同一主题提交，沿用 AI-08，不新增同义条目。

## 11. 尚未闭环的优先级

### P0：上线前必须完成

1. 完成阿里云远端镜像拉取和四容器启动，不能只停留在配置提交。
2. 执行数据库迁移，验证后端健康检查与 Nginx 反向代理。
3. 完成公网 IP HTTPS 签发、自动续期和 Secure Cookie 验证。
4. 实测邮箱验证码、密码重置、旧账号登录和会话撤销。
5. 验证 PostgreSQL、附件和配置备份可在隔离环境恢复。
6. 观察 2C2G + Swap 下的内存、日志和容器重启情况。

### P1：下一轮产品改造

1. 以当前真实页面为实施基线，功能审计只作辅助；V11 已退回。一次只评审一个区域，保留位置、顺序、密度和交互行为；结构或行为变化单独确认，不把审美方向认可当作整页批准。
2. 优先解决 AI 面板打开后正文过窄、标题重复、修改预览难读三个 P0 体验问题。
3. 再统一目录、编辑器、AI 面板、草稿和修改预览的组件语言。
4. 补搜索初始态、移动端顶栏和深色模式硬编码清理。
5. 每个模块单独提交，附截图、测试和回退说明。

### P2：工程与交付改进

1. 增加开发环境自检，启动前检查 Node、Python、Docker、端口和必需环境变量。
2. 增加远端部署 smoke test 和“生成中停止 → 刷新 → 恢复 → 保存”E2E。
3. 持续维护已新增的 `design/README.md`，每轮更新当前候选、批准状态、探索稿和已废弃方向。

## 12. 后续协作规则

结合本轮反复暴露的问题，后续建议固定以下规则：

1. 先明确约束再选方案：用户、预算、设备、部署形态和必须保留的功能先确定。
2. UI 设计必须逐项映射现有组件与真实状态，概念稿不能冒充可实施方案。
3. 设计稿通过后才改业务代码；设计稿、基础 Token、单个模块和运维配置分别提交。
4. 每次提交只包含一个主题，提交信息写清“改了什么、为什么、如何验证”。
5. 不提交秘密与运行数据；需要跨机器迁移时，用独立备份流程解决。
6. “构建通过”不等于“可上线”，必须补真实环境、数据恢复和关键业务链路验收。
7. 临时预览、外部生成服务和镜像代理都属于易失依赖，交付时必须说明当前是否仍可用。
